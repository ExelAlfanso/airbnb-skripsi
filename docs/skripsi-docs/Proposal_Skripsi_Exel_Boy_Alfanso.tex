\section{Keminatan dan Bidang Penelitian}
Pada skripsi ini, keminatan saya adalah MGM (Multimedia, Game, dan Mobile) dan spesifik Bidang penelitian yang diambil khususnya pada kajian pengembangan aplikasi web, performa antarmuka web responsif, serta evaluasi framework frontend modern pada perangkat bergerak.

\section{Jenis Penelitian}
Jenis penelitian ini adalah penelitian implementatif dengan pendekatan pengembangan. Penelitian ini menghasilkan artefak berupa prototipe mobile web listing properti yang dikembangkan dalam dua versi frontend, yaitu VueJS dan Svelte. Kedua frontend menggunakan service backend yang sama berbasis ElysiaJS dengan Eden Treaty sebagai type-safe API client. Setelah prototipe dikembangkan, dilakukan pengujian dan analisis perbandingan performa menggunakan Core Web Vitals dan metrik efisiensi sumber daya.

\section{Judul / Topik Skripsi}
Judul/topik yang akan saya bawa pada skripsi ini adalah Analisis Perbandingan Performa Framework Frontend VueJS dan Svelte Menggunakan Core Web Vitals dan Efisiensi Sumber Daya pada Prototipe Mobile Web Listing Properti Berbasis Studi Kasus Airbnb dengan Service Backend ElysiaJS dan Eden Treaty.

\section{Latar Belakang}
Perkembangan aplikasi web modern menuntut website untuk memiliki performa yang cepat, responsif, dan efisien dalam penggunaan sumber daya. Kebutuhan tersebut menjadi semakin penting pada website berbasis listing yang menampilkan banyak konten visual dan elemen antarmuka secara bersamaan. Pada website listing properti, misalnya, halaman dapat memuat gambar properti, informasi lokasi, harga, rating, serta berbagai komponen interaktif seperti pencarian, penyaringan, pengurutan, dan pemuatan data tambahan. Karakteristik tersebut menyebabkan sisi frontend memiliki peran penting terhadap waktu pemuatan halaman, respons terhadap interaksi pengguna, stabilitas tampilan, serta jumlah sumber daya yang perlu diproses oleh browser.

VueJS dan Svelte merupakan framework frontend berbasis komponen yang dapat digunakan untuk membangun antarmuka web interaktif. Meskipun memiliki tujuan yang serupa, keduanya menggunakan pendekatan berbeda dalam proses pembaruan antarmuka. VueJS menggunakan sistem reaktivitas yang bekerja bersama mekanisme Virtual DOM pada saat aplikasi berjalan, sedangkan Svelte menggunakan pendekatan berbasis compiler dengan mengompilasi komponen menjadi kode JavaScript pada proses build. Perbedaan pendekatan tersebut berpotensi menghasilkan karakteristik performa yang berbeda, baik dari sisi proses rendering, jumlah JavaScript yang dikirimkan ke browser, penggunaan sumber daya, maupun respons aplikasi ketika terjadi perubahan data.

Penelitian sebelumnya telah menunjukkan bahwa perbedaan strategi rendering pada framework frontend dapat menghasilkan karakteristik performa yang berbeda. (Ollila, M\"akitalo and Mikkonen, 2022) membandingkan strategi rendering Angular, React, Vue, Svelte, dan Blazor menggunakan sejumlah benchmark untuk mengukur perubahan biaya rendering seiring meningkatnya kompleksitas aplikasi. Penelitian tersebut menunjukkan adanya perbedaan pola performa berdasarkan strategi rendering yang digunakan oleh masing-masing framework. Selain itu, (Putra et al., 2025) membandingkan Svelte, React, dan Vue menggunakan aplikasi web sederhana yang dibuat secara identik dengan pengukuran berupa rendering time, bundle size, penggunaan memori saat idle, dan efisiensi operasi DOM. Penelitian tersebut menunjukkan bahwa perbedaan arsitektur framework dapat memengaruhi performa teknis aplikasi.

Meskipun demikian, penelitian terdahulu tersebut masih berfokus pada benchmark rendering atau implementasi aplikasi yang relatif sederhana. Kondisi tersebut belum sepenuhnya menggambarkan karakteristik aplikasi web yang memiliki banyak konten visual serta melibatkan beberapa bentuk interaksi dan perubahan data dalam satu aplikasi. Oleh karena itu, masih diperlukan kajian mengenai bagaimana perbedaan pendekatan VueJS dan Svelte menghasilkan karakteristik performa ketika diterapkan pada prototipe aplikasi yang memiliki workload lebih representatif, seperti website listing properti yang mencakup pemuatan sejumlah gambar dan komponen berulang, pencarian, penyaringan, pengurutan, pemuatan data tambahan, dan navigasi menuju detail properti. Selain itu, evaluasi yang menggabungkan metrik performa yang berorientasi pada pengalaman pengguna melalui Core Web Vitals dengan efisiensi sumber daya dan respons interaksi dapat memberikan gambaran yang lebih menyeluruh mengenai perbedaan performa kedua framework.

Berdasarkan kesenjangan tersebut, penelitian ini mengembangkan dua prototipe website listing properti menggunakan VueJS dan Svelte dengan fitur dan perilaku yang dibuat setara. Kedua implementasi menggunakan desain, dataset, aset, struktur konten, dan service backend yang sama. ElysiaJS digunakan sebagai service backend untuk menyediakan data melalui API, sedangkan Eden Treaty digunakan untuk mendukung komunikasi API yang type-safe antara frontend dan backend. Kesetaraan tersebut diterapkan agar perbedaan hasil pengujian dapat lebih difokuskan pada karakteristik implementasi frontend masing-masing framework, bukan akibat perbedaan data, desain, fitur, atau layanan backend.

Prototipe yang dikembangkan mengacu pada karakteristik umum website listing properti modern, khususnya pola penyajian daftar properti yang kaya konten visual serta mendukung fitur seperti pencarian, penyaringan, pengurutan, halaman detail, dan pemuatan data secara bertahap. Airbnb dapat digunakan sebagai salah satu referensi karakteristik antarmuka dan pola interaksi pada domain tersebut. Namun, penelitian ini tidak bertujuan untuk mereplikasi Airbnb secara penuh maupun mengevaluasi teknologi yang digunakan oleh Airbnb, melainkan menggunakan karakteristik website listing properti sebagai konteks untuk melakukan perbandingan performa VueJS dan Svelte.

\chapter{LANDASAN KEPUSTAKAAN}

\section{Website Responsif}
Website responsif merupakan website yang dirancang agar tampilan dan tata letaknya dapat menyesuaikan berbagai ukuran layar, termasuk desktop, tablet, dan mobile. Pada tampilan mobile, website responsif perlu memperhatikan penyusunan konten, ukuran elemen interaktif, keterbacaan teks, navigasi, serta efisiensi resource agar tetap nyaman digunakan. Dalam penelitian ini, responsivitas mobile menjadi konteks pengujian karena prototipe listing properti akan diuji pada viewport mobile.

\section{Framework Frontend}
Framework frontend merupakan kerangka kerja yang digunakan untuk membangun antarmuka pengguna pada aplikasi web. Framework frontend membantu pengembang dalam menyusun komponen, mengelola struktur aplikasi, mengatur interaksi pengguna, dan membangun tampilan web modern. (Ferreira, Borges and Valente, 2022) menjelaskan bahwa framework frontend JavaScript seperti Vue, React, Angular, Ember, dan Backbone digunakan untuk membangun antarmuka web modern berbasis komponen. Selain itu, (Sofi'ie and Qoiriah, 2023) menyatakan bahwa framework frontend menjadi komponen penting dalam pengembangan website karena dapat membantu proses pengembangan, manajemen kode, performa, dan konsistensi aplikasi.

\section{Vue JS}
Vue.js adalah framework frontend JavaScript yang digunakan untuk membangun antarmuka web berbasis komponen. (Ferreira, Borges and Valente, 2022) menjelaskan bahwa Vue merupakan progressive framework yang menggunakan pola Model-View-View\\
Model (MVVM) dan mendukung mekanisme one-way maupun two-way data binding. Dalam penelitian lain, (Sofi'ie and Qoiriah, 2023) menyebutkan bahwa Vue memiliki karakteristik struktur aplikasi yang sederhana dan kemampuan pengelolaan data yang mudah. Pada penelitian ini, Vue.js digunakan sebagai salah satu framework frontend yang dibandingkan dalam pengembangan prototipe website responsif listing properti.

\section{Svelte}
Svelte adalah framework frontend berbasis komponen yang menggunakan pendekatan compiler-based. Berbeda dengan framework yang membawa runtime besar ke browser, Svelte mengkompilasi komponen menjadi JavaScript pada saat proses build. Dengan pendekatan ini, Svelte dapat menghasilkan kode yang lebih spesifik terhadap kebutuhan komponen dan berpotensi mengurangi beban runtime pada browser. Karakteristik ini relevan untuk website responsif yang memiliki banyak komponen berulang dan membutuhkan antarmuka yang tetap responsif pada tampilan mobile.

\section{Core Web Vitals}
Core Web Vitals merupakan kumpulan metrik yang digunakan untuk mengukur kualitas pengalaman pengguna pada website. Metrik ini mencakup Largest Contentful Paint, Interaction to Next Paint, dan Cumulative Layout Shift. LCP digunakan untuk mengukur waktu munculnya konten utama, INP digunakan untuk mengukur respons interaksi, dan CLS digunakan untuk mengukur stabilitas visual halaman. Dalam penelitian ini, Core Web Vitals digunakan sebagai metrik utama untuk membandingkan performa prototipe VueJS dan Svelte. (Andriyanai et al., 2025)

\subsection{Largest Contentful Paint}
Largest Contentful Paint (LCP) merupakan metrik yang mengukur waktu yang dibutuhkan hingga elemen konten terbesar pada area tampilan (viewport) berhasil ditampilkan kepada pengguna. Elemen yang diperhitungkan dapat berupa gambar, elemen gambar yang terdapat di dalam SVG, gambar latar tertentu, video, maupun blok teks yang berukuran besar. Dengan demikian, LCP digunakan sebagai indikator untuk mengetahui seberapa cepat konten utama suatu halaman dapat dilihat oleh pengguna.

\subsection{Interaction to Next Paint}
Interaction to Next Paint (INP) merupakan metrik Core Web Vitals yang digunakan untuk mengukur tingkat responsivitas suatu halaman terhadap interaksi pengguna. INP mengamati latensi interaksi seperti klik, sentuhan, dan input menggunakan papan ketik selama pengguna mengakses halaman. Nilai INP merepresentasikan waktu antara terjadinya interaksi pengguna hingga browser dapat menampilkan pembaruan visual berikutnya sebagai respons terhadap interaksi tersebut.

Berbeda dengan metrik yang hanya mengukur interaksi pertama, INP mempertimbangkan berbagai interaksi yang terjadi sepanjang penggunaan halaman dan menggunakan interaksi dengan latensi yang paling tinggi dengan mekanisme tertentu untuk mengabaikan outlier. Nilai INP yang rendah menunjukkan bahwa halaman mampu memberikan umpan balik visual secara konsisten dalam waktu yang singkat. Google menetapkan INP sebesar 200 milidetik atau kurang sebagai kategori baik, sedangkan nilai lebih dari 500 milidetik dikategorikan buruk.

\subsection{Cumulative Layout Shift}
Cumulative Layout Shift (CLS) merupakan metrik yang mengukur stabilitas visual halaman berdasarkan perubahan posisi elemen yang terjadi secara tidak terduga selama halaman digunakan. Perubahan tata letak dapat terjadi ketika suatu elemen berpindah setelah elemen lain selesai dimuat, misalnya gambar yang tidak memiliki dimensi yang ditentukan sebelumnya atau konten yang dimasukkan secara dinamis. CLS menghitung kelompok perubahan tata letak tidak terduga yang paling signifikan selama siklus hidup halaman.

Berbeda dengan LCP dan INP yang menggunakan satuan waktu, CLS merupakan nilai tanpa satuan. Nilai yang semakin mendekati nol menunjukkan bahwa tampilan halaman semakin stabil. Google menetapkan nilai CLS sebesar 0,1 atau kurang sebagai kategori baik. Stabilitas visual penting karena perubahan posisi elemen secara tiba-tiba dapat mengganggu pengguna ketika membaca konten atau berinteraksi dengan suatu elemen antarmuka.

\section{Efisiensi Sumber Daya}
Efisiensi sumber daya berkaitan dengan seberapa besar resource yang dibutuhkan oleh aplikasi web untuk dimuat dan dijalankan di browser. Aspek ini dapat dianalisis melalui JavaScript bundle size, total transferred size, dan request count. Metrik tersebut penting karena ukuran resource yang besar dapat memengaruhi waktu muat halaman, terutama pada tampilan mobile dan kondisi jaringan terbatas.

\section{ElysiaJS dan Eden Treaty}
ElysiaJS merupakan framework backend berbasis Bun dan TypeScript yang digunakan untuk membangun service API. Dalam penelitian ini, ElysiaJS digunakan sebagai backend yang sama untuk kedua frontend agar dataset, endpoint, dan response shape tetap konsisten. Eden Treaty digunakan sebagai type-safe API client agar komunikasi antara frontend dan backend memiliki kontrak tipe yang lebih aman dan konsisten.

\section{Website Listing Properti}
Website listing properti adalah website yang menampilkan daftar properti dalam bentuk katalog atau grid. Website jenis ini umumnya memiliki fitur pencarian, filter, sorting, pagination, dan halaman detail. Karakteristik tersebut cocok digunakan sebagai studi kasus untuk menguji performa frontend karena melibatkan pemuatan data visual, pengelolaan daftar data, serta interaksi pengguna.

\subsection{Unit Testing}
Unit testing adalah pengujian perangkat lunak yang dilakukan pada bagian kecil dari sistem, seperti fungsi, modul, atau komponen tertentu, secara terpisah dari keseluruhan aplikasi. Pengujian ini bertujuan untuk memastikan bahwa setiap bagian logic menghasilkan keluaran yang sesuai dengan input yang diberikan. Dalam penelitian ini, unit testing digunakan untuk memvalidasi kesetaraan logic pada implementasi VueJS dan Svelte, seperti pencarian, filter, sorting, pagination, dan formatting data properti.

\subsection{Integration Testing}
Integration testing adalah pengujian perangkat lunak yang dilakukan untuk memastikan bahwa beberapa modul atau komponen yang saling terhubung dapat bekerja bersama sesuai dengan kebutuhan sistem. Berbeda dengan unit testing yang berfokus pada bagian kecil secara terpisah, integration testing menguji hubungan antarbagian, seperti interaksi antara frontend dengan backend, pemrosesan data dari API, serta kesesuaian data yang ditampilkan pada antarmuka. Dalam penelitian ini, integration testing digunakan untuk memvalidasi bahwa prototipe VueJS dan Svelte dapat mengambil, mengolah, dan menampilkan data dari service backend ElysiaJS dengan hasil yang setara sebelum dilakukan pengujian performa.

\subsection{End-to-End Testing}
End-to-end testing adalah pengujian perangkat lunak yang dilakukan dengan mensimulasikan alur penggunaan aplikasi dari sisi pengguna secara menyeluruh. (Azizullah, Rahayudi and Priyambadha, 2026) menjelaskan bahwa end-to-end testing mensimulasikan skenario pengguna asli yang berinteraksi dengan aplikasi dari awal hingga akhir untuk memastikan komponen dan subsistem berjalan bersama sesuai harapan. Dalam penelitian ini, end-to-end testing digunakan untuk memvalidasi alur penggunaan pada kedua prototipe, seperti membuka halaman listing, melakukan pencarian, menerapkan filter, membuka halaman detail, dan menggunakan wishlist dummy.

\subsection{Web Performance Testing}
Web performance testing merupakan proses pengukuran terhadap performa aplikasi web untuk mengetahui bagaimana halaman dimuat, ditampilkan, dan merespons aktivitas pengguna. Pengukuran performa web dapat mencakup aspek seperti waktu pemuatan, proses rendering, responsivitas, penggunaan jaringan, serta penggunaan sumber daya komputasi pada browser. W3C melalui Web Performance Working Group mengembangkan berbagai mekanisme dan API yang memungkinkan pengukuran performa jaringan, rendering, responsivitas, interaktivitas, penggunaan memori, dan penggunaan CPU pada aplikasi web.

Pengujian performa web secara umum dapat dibedakan menjadi pengukuran lab dan field. Lab testing dilakukan pada lingkungan yang dikontrol dengan kondisi perangkat dan jaringan tertentu sehingga pengujian dapat dilakukan secara berulang dan konsisten. Sementara itu, field testing menggunakan data dari pengguna nyata dengan variasi perangkat, jaringan, dan kondisi penggunaan yang terjadi sebenarnya. Kedua pendekatan memiliki tujuan yang berbeda, dengan pengujian lab lebih sesuai untuk pengembangan, eksperimen, dan identifikasi regresi performa, sedangkan data field digunakan untuk mengetahui performa yang benar-benar dialami pengguna.

Salah satu alat yang dapat digunakan untuk melakukan pengujian performa pada lingkungan lab adalah Google Lighthouse. Lighthouse merupakan alat audit otomatis dan open-source yang dapat mengevaluasi sejumlah aspek kualitas halaman web, termasuk performa, aksesibilitas, dan SEO. Pada aspek performa, hasil Lighthouse dapat digunakan untuk memperoleh sejumlah metrik dan diagnosis terkait proses pemuatan serta rendering halaman.

\subsection{User Experience}
User Experience (UX) merupakan pengalaman yang muncul dari interaksi pengguna dengan suatu sistem, produk, atau layanan. Berdasarkan ISO 9241-210, pengalaman pengguna mencakup berbagai persepsi dan respons pengguna, seperti emosi, keyakinan, preferensi, persepsi, respons fisik dan psikologis, perilaku, serta pencapaian yang terjadi sebelum, selama, maupun setelah penggunaan suatu sistem. Dengan demikian, UX memiliki cakupan yang lebih luas daripada sekadar kemampuan pengguna dalam menyelesaikan suatu tugas.

Pengalaman pengguna pada aplikasi web dapat dipengaruhi oleh berbagai aspek antarmuka dan kualitas sistem. Selain desain visual dan kemudahan penggunaan, performa teknis juga dapat menjadi bagian yang mendukung pengalaman pengguna karena menentukan seberapa cepat konten dapat ditampilkan, seberapa responsif sistem terhadap tindakan pengguna, serta seberapa stabil tampilan ketika digunakan. Core Web Vitals sendiri dikembangkan untuk merepresentasikan aspek pengalaman pengguna pada web yang berkaitan dengan pemuatan, responsivitas, dan kestabilan visual.

\subsection{Usability Testing}
Usability berkaitan dengan kemampuan suatu sistem, produk, atau layanan untuk digunakan oleh pengguna dalam mencapai tujuan tertentu dalam konteks penggunaan yang ditentukan. ISO 9241-11 memberikan kerangka untuk memahami dan menerapkan konsep usability pada sistem interaktif. Aspek usability pada umumnya berkaitan dengan sejauh mana pengguna mampu menyelesaikan tujuan secara efektif, efisien, dan memperoleh tingkat kepuasan tertentu ketika menggunakan suatu sistem.

Usability testing merupakan metode evaluasi yang melibatkan pengguna untuk berinteraksi secara langsung dengan suatu antarmuka melalui serangkaian tugas yang merepresentasikan aktivitas penggunaan sebenarnya. Dalam pelaksanaannya, peserta diminta menjalankan tugas tertentu sementara peneliti mengamati perilaku, keberhasilan penyelesaian tugas, kesulitan yang muncul, serta umpan balik yang diberikan peserta. Tugas yang diberikan sebaiknya merepresentasikan tujuan pengguna sebenarnya agar temuan pengujian relevan terhadap kondisi penggunaan aplikasi.

\subsection{System Usability Scale (SUS)}
System Usability Scale (SUS) merupakan kuesioner terstandar yang dikembangkan oleh Brooke (1996) untuk mengukur tingkat kebolehgunaan (\textit{usability}) suatu sistem atau produk secara cepat, andal, dan efisien. SUS terdiri atas 10 item pertanyaan menggunakan skala Likert 5 poin, mulai dari angka 1 (\textit{Sangat Tidak Setuju}) hingga 5 (\textit{Sangat Setuju}). Item pertanyaan pada SUS disusun secara selang-seling antara pernyataan bernada positif pada item bernomor ganjil (1, 3, 5, 7, 9) dan pernyataan bernada negatif pada item bernomor genap (2, 4, 6, 8, 10).

Skor SUS dihitung dengan mengonversi nilai dari setiap item pertanyaan terlebih dahulu. Untuk item bernomor ganjil, kontribusi skor diperoleh dari nilai jawaban dikurangi 1. Sementara untuk item bernomor genap, kontribusi skor diperoleh dari 5 dikurangi nilai jawaban. Jumlah dari keseluruhan kontribusi skor 10 item tersebut kemudian dikalikan dengan 2,5 untuk menghasilkan total skor SUS dalam rentang 0 hingga 100.

Secara matematis, formula perhitungan skor SUS untuk satu responden dirumuskan sebagai berikut:

\begin{equation}
\text{Skor SUS} = 2{,}5 \times \left[ \sum_{i \in \{1, 3, 5, 7, 9\}} (R_i - 1) + \sum_{i \in \{2, 4, 6, 8, 10\}} (5 - R_i) \right]
\end{equation}

\noindent Keterangan:
\begin{itemize}[label={--}]
    \item $R_i$ = Nilai jawaban responden pada item pertanyaan ke-$i$ (rentang 1--5).
    \item $(R_i - 1)$ = Kontribusi skor untuk item bernomor ganjil (pernyataan positif).
    \item $(5 - R_i)$ = Kontribusi skor untuk item bernomor genap (pernyataan negatif).
    \item $2{,}5$ = Pengali konversi agar total skor berada pada rentang 0--100.
\end{itemize}

Hasil skor rata-rata SUS dari seluruh responden kemudian diinterpretasikan untuk menentukan tingkat keberterimaan (\textit{acceptability}), tingkatan (\textit{grade scale}), dan predikat (\textit{adjective rating}) dari sistem yang dievaluasi (Bangor, Kortum and Miller, 2008). Skor SUS di atas 68 umumnya dikategorikan di atas rata-rata (\textit{above average}) atau berada pada kategori dapat diterima (\textit{acceptable}).

\subsection{Vitest}
Vitest adalah testing framework yang digunakan untuk menjalankan pengujian unit pada aplikasi berbasis JavaScript atau TypeScript. Vitest dipilih karena dapat digunakan pada ekosistem frontend modern dan mendukung proses pengujian logic secara cepat. Dalam penelitian ini, Vitest digunakan untuk menguji fungsi-fungsi pengolahan data pada prototipe VueJS dan Svelte agar logic yang digunakan pada kedua implementasi menghasilkan keluaran yang setara.

\subsection{Playwright}
Playwright adalah alat pengujian end-to-end yang digunakan untuk menjalankan skenario penggunaan aplikasi melalui browser secara otomatis. (Azizullah, Rahayudi and Priyambadha, 2026) menjelaskan bahwa Playwright mendukung otomasi pengujian end-to-end pada aplikasi web dan dapat berjalan pada beberapa browser utama seperti Chromium, Firefox, dan WebKit. Dengan kemampuan tersebut, Playwright digunakan dalam penelitian ini untuk memastikan fitur dan alur interaksi pada prototipe Vue.js and Svelte berjalan setara pada viewport mobile serta bertindak sebagai \textit{interaction driver} pada pengujian performa responsivitas interaksi (INP).

\subsection{Google Lighthouse}
Google Lighthouse merupakan alat audit otomatis dan open-source yang digunakan untuk mengevaluasi kualitas halaman web. Lighthouse dapat dijalankan melalui Chrome DevTools, command line, maupun sebagai modul Node.js. Proses audit dilakukan dengan menjalankan serangkaian pengujian terhadap suatu halaman web kemudian menghasilkan laporan yang mencakup beberapa aspek, salah satunya performa halaman.

Pada aspek performa, Lighthouse memberikan sejumlah metrik, diagnostics, dan insights yang dapat digunakan untuk menganalisis proses pemuatan dan rendering halaman. Nilai Performance Score Lighthouse diperoleh dari kombinasi berbobot beberapa metrik performa. Namun, hasil pengukuran dapat mengalami variasi akibat kondisi lingkungan pengujian sehingga pengujian berulang diperlukan untuk memperoleh hasil yang lebih representatif.

\subsection{Chrome DevTools}
Chrome DevTools merupakan sekumpulan alat pengembangan yang terintegrasi pada browser Google Chrome dan digunakan untuk melakukan inspeksi, debugging, serta analisis terhadap aplikasi web. Chrome DevTools menyediakan berbagai panel, seperti Elements, Network, Performance, dan Memory, yang dapat digunakan untuk mengamati struktur halaman, aktivitas jaringan, proses eksekusi aplikasi, serta penggunaan sumber daya pada browser.

Dalam analisis performa web, Network Panel dapat digunakan untuk merekam aktivitas permintaan jaringan ketika halaman dimuat. Informasi yang tersedia pada panel ini mencakup sumber daya yang diminta oleh halaman, ukuran data yang ditransfer, jumlah permintaan, waktu pemuatan, serta jenis sumber daya yang digunakan. Data tersebut dapat digunakan untuk mengetahui seberapa besar sumber daya yang diperlukan oleh suatu aplikasi ketika dijalankan pada browser.

Selain itu, Performance Panel dapat digunakan untuk merekam dan menganalisis aktivitas aplikasi selama proses pemuatan halaman maupun ketika pengguna melakukan interaksi. Panel ini menyediakan informasi mengenai aktivitas main thread, eksekusi JavaScript, proses scripting, rendering, dan layout. Informasi tersebut dapat digunakan untuk mengidentifikasi aktivitas komputasi yang berpotensi menjadi bottleneck pada aplikasi web.

function filterProperties(properties, query, filters):
    hasil = properties

    if query tidak kosong:
        hasil = filter berdasarkan nama atau lokasi

    if priceRange tersedia:
        hasil = filter berdasarkan rentang harga

\subsection{Pengujian LCP dan CLS}
\label{sec:pengujian-lcp-cls}
Google Lighthouse digunakan untuk mengukur performa pemuatan dan stabilitas tampilan kedua prototipe pada viewport perangkat bergerak dalam mode \textit{production build}. Selain itu, beberapa metrik diagnostik Lighthouse seperti First Contentful Paint (FCP), Total Blocking Time (TBT), Speed Index, dan Performance Score digunakan sebagai data pendukung dalam proses analisis. Metrik diagnostik tersebut bukan merupakan bagian dari Core Web Vitals.

Prosedur pengujian dilakukan dengan alur berikut:
\begin{enumerate}
    \item Membangun \textit{production build} pada kedua prototipe.
    \item Menjalankan aplikasi pada lingkungan pengujian yang telah dikonfigurasi.
    \item Menyiapkan kondisi pengujian yang sama (browser, viewport, cache policy).
    \item Menjalankan Google Lighthouse pada masing-masing prototipe.
    \item Menyimpan hasil metrik dari setiap pengujian.
    \item Mengulangi pengujian sebanyak $n$ kali.
    \item Menghitung nilai representatif (median) dari seluruh pengulangan.
\end{enumerate}

\subsection{Pengujian Interaction to Next Paint}
\label{sec:pengujian-inp}
Pengukuran Interaction to Next Paint (INP) pada penelitian ini dilakukan melalui metode pengujian laboratorium otomatis (\textit{automated scripted testing}) menggunakan Playwright sebagai \textit{interaction driver} dan \textit{Event Timing API} browser Google Chrome sebagai perekam latensi interaksi secara langsung. Metode pengujian otomatis berbasis skrip ini dipilih agar seluruh interaksi dapat dijalankan secara presisi dan deterministik pada kondisi lingkungan yang identik, sehingga variasi latensi yang dihasilkan murni mencerminkan efisiensi penanganan interaksi oleh masing-masing framework. Prosedur otomasi dan perekaman durasi interaksi dirumuskan dalam bentuk pseudocode pada Kode~\ref{code:inp-pseudocode}.

\begin{lstlisting}[language=TypeScript, caption={Pseudocode Algoritme Pengukuran INP}, label={code:inp-pseudocode}]
FOR setiap framework
    FOR setiap skenario
        FOR setiap run
            Buat browser context baru
            Atur viewport 390 x 844
            Terapkan CPU throttling 4x
            Pasang PerformanceObserver (Event Timing)
            Buka production build
            Jalankan interaksi menggunakan Playwright
            Rekam interaction timing
            Simpan nilai INP
        END FOR

        Hitung median
        Hitung IQR
    END FOR
END FOR
\end{lstlisting}

Pengukuran dilakukan dengan menyuntikkan \textit{PerformanceObserver} ke dalam konteks halaman browser. Potongan kode setup perekaman \textit{Event Timing API} ditunjukkan pada Kode~\ref{code:perf-observer}.

\begin{lstlisting}[language=TypeScript, caption={Setup PerformanceObserver untuk Merekam Event Timing API Browser}, label={code:perf-observer}]
const observer = new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    if (entry.interactionId > 0) {
      interactions.push({
        interactionId: entry.interactionId,
        duration: entry.duration
      });
    }
  }
});

observer.observe({
  type: "event",
  buffered: true,
  durationThreshold: 16
});
\end{lstlisting}

Pengujian dijalankan terhadap tiga skenario interaksi utama. Salah satu contoh potongan skenario otomatisasi Playwright pada fitur \textit{advanced filter} ditunjukkan pada Kode~\ref{code:playwright-example}.

\begin{lstlisting}[language=TypeScript, caption={Potongan Skenario Otomatisasi Playwright pada Advanced Filter}, label={code:playwright-example}]
await page.getByLabel("Lokasi").selectOption({ label: "Senggigi, Lombok" });
await page.getByLabel("Tipe").selectOption({ label: "Villa" });
await page.getByText("Filter lanjutan", { exact: true }).click();

await page.getByLabel("Kitchen").check();

\end{lstlisting}

\subsection{Pengujian Efisiensi Sumber Daya}
\label{sec:pengujian-efisiensi}
Pengujian efisiensi sumber daya dilakukan menggunakan hasil \textit{production build} dan Chrome DevTools, khususnya melalui Network Panel. Metrik yang diamati meliputi:
\begin{itemize}
    \item \textbf{JavaScript bundle size}: ukuran kode JavaScript yang perlu dikirim dan diproses oleh browser.
    \item \textbf{Total transferred size}: keseluruhan data yang ditransfer melalui jaringan ketika halaman dimuat.
    \item \textbf{Request count}: jumlah permintaan sumber daya yang dilakukan oleh browser.
\end{itemize}

Seluruh pengukuran dilakukan pada halaman, dataset, aset, browser, dan kondisi jaringan yang sama. Dengan demikian, perbandingan efisiensi sumber daya dapat digunakan sebagai data pendukung untuk menjelaskan perbedaan karakteristik performa komputasional antara VueJS dan Svelte.

\section{Evaluasi User Experience dan Usability}
\label{sec:evaluasi-ux-usability}

\subsection{Partisipan Penelitian}
\label{sec:partisipan}
% TODO: lengkapi jumlah dan karakteristik responden setelah ditentukan.
Evaluasi \textit{User Experience} dan \textit{usability} melibatkan responden yang mewakili target pengguna prototipe website listing properti. Kriteria inklusi meliputi pengguna yang memiliki pengalaman mengakses website melalui perangkat bergerak. Metode pengambilan sampel dan jumlah responden akan ditentukan sebelum pelaksanaan evaluasi.

\subsection{Skenario Pengujian}
\label{sec:skenario-ux}
Responden diminta menjalankan rangkaian tugas yang sama pada prototipe VueJS dan Svelte. Tugas yang diberikan meliputi:
\begin{enumerate}
    \item Mencari properti berdasarkan kata kunci.
    \item Menggunakan \textit{advanced filter} untuk menyaring properti.
    \item Mengurutkan daftar properti.
    \item Membuka halaman detail properti.
    \item Menambahkan properti ke wishlist.
\end{enumerate}

\subsection{Prosedur Pengujian}
\label{sec:prosedur-ux}
Pengujian menggunakan desain \textit{within-subject}: setiap responden mencoba kedua prototipe. Untuk mengurangi \textit{order effect}, diterapkan \textit{counterbalancing} sebagai berikut:
\begin{itemize}
    \item \textbf{Kelompok A}: VueJS terlebih dahulu, kemudian Svelte.
    \item \textbf{Kelompok B}: Svelte terlebih dahulu, kemudian VueJS.
\end{itemize}

Setelah menggunakan masing-masing prototipe, responden mengisi kuesioner User Experience Questionnaire (UEQ) dan System Usability Scale (SUS). Skenario, data, tampilan, dan kondisi penggunaan dibuat setara pada kedua prototipe.

\subsection{User Experience Questionnaire}
\label{sec:ueq-metode}
User Experience Questionnaire (UEQ) diberikan kepada responden setelah menyelesaikan rangkaian tugas pada masing-masing prototipe. Hasil UEQ dihitung pada enam skala, yaitu \textit{Attractiveness}, \textit{Perspicuity}, \textit{Efficiency}, \textit{Dependability}, \textit{Stimulation}, dan \textit{Novelty}. Nilai UEQ pada prototipe VueJS dan Svelte kemudian dibandingkan.

\subsection{System Usability Scale}
\label{sec:sus-metode}
System Usability Scale (SUS) diberikan setelah responden menggunakan masing-masing prototipe. SUS terdiri atas 10 item dengan skala Likert 5 poin. Skor akhir berada pada rentang 0--100. Perhitungan skor SUS menggunakan formula yang telah dijelaskan pada Bab~2. Skor SUS pada prototipe VueJS dan Svelte kemudian dibandingkan.

Hasil pengujian berulang dianalisis menggunakan statistik deskriptif. Nilai representatif yang digunakan meliputi median, minimum, maksimum, dan \textit{interquartile range} (IQR).

\begin{equation}
\label{eq:iqr}
\text{IQR} = Q_3 - Q_1
\end{equation}

Median digunakan karena hasil pengujian performa pada browser dapat mengalami variasi antar-run dan median lebih tahan terhadap nilai ekstrem dibandingkan satu hasil pengukuran tunggal.

\end{itemize}
